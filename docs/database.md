# 🗄️ 데이터베이스 설계

스키마 원본은 [`../app/db/schema.sql`](../app/db/schema.sql)이다. 이 문서는 그
파일을 옮겨 적지 않는다. **컬럼 목록을 보고는 알 수 없는 판단**만 적는다.

---

## 🧩 설계 원칙

**샘플 응답에서 실제로 확인된 필드만 만든다.** `samples/`에 받아둔 실제 응답에
없는 컬럼은 두지 않는다. 스펙 문서에 적혀 있어도 실제로 오지 않는 값이 있고
(`form`이 그렇다), 미리 만든 빈 컬럼은 "채워질 예정"과 "영영 null"을 구분할 수
없게 만든다.

**외부 스키마를 그대로 저장하지 않는다.** camelCase → snake_case로 바꾸고,
쓰지 않기로 한 필드는 저장 단계에서 버린다. 응답 구조가 바뀌어도 변환
지점(`ingest/mappers.py`) 하나만 고치면 된다.

**ORM을 쓰지 않는다.** stdlib `sqlite3` + 손으로 쓴 SQL이다. 테이블이 여섯 개고
쿼리가 열 개 남짓이라 ORM이 얹어 주는 추상화보다 "이 요청이 어떤 SQL을 내보내는가"가
한눈에 보이는 편이 낫다.

---

## 📊 테이블

여섯 개다. 참조 방향은 아래와 같다.

```
competitions ──▶ seasons ──┐
      │                    ├──▶ standings ──▶ teams
      └────────────────────┴──▶ matches   ──▶ teams (home / away)

ingest_runs   (독립. FK 없음)
```

### teams — 팀 마스터

| 컬럼 | 비고 |
| --- | --- |
| `id` | PK. 외부 id를 그대로 쓴다 |
| `name` | NOT NULL |
| `short_name` `tla` `crest` | 인라인 스냅샷에서 빠질 수 있어 nullable |
| `updated_at` | 마지막 갱신 시각 (UTC) |

**왜 외부 id가 그대로 PK인가** — 팀 id는 리그·시즌과 무관하게 전역 고유하다.
자체 시퀀스를 두고 매핑 테이블을 만들 이유가 없고, `/teams/57` 경로에 그대로 쓴다.

**이 테이블은 전용 엔드포인트로 채워지지 않는다.** 팀 정보는 순위표 행과 경기
양쪽에 인라인으로 실려 오고, 그 스냅샷으로 마스터를 갱신한다. 팀 목록을 따로
호출하면 5리그 x 1콜이 더 나가는데, 분당 10회 예산에 그만한 여유가 없다.
대신 **인라인 스냅샷은 슬림해서 일부 필드가 빠진다** — 그래서 덮어쓰기에
`COALESCE`를 쓴다 ([`ingestion.md`](ingestion.md) 참고).

### competitions — 대회

`code`에 `UNIQUE`를 건다. 라우팅 키가 `code`라 code로 찾는 조회가 기본이고,
같은 code가 둘일 수 없다는 사실을 DB가 보증하게 한다.

`current_season_id`는 FK를 걸지 않았다. 쓰기 순서상 대회를 시즌보다 먼저 써야
하는데(`competitions → seasons`), FK를 걸면 아직 없는 시즌을 참조하게 되어
첫 삽입이 실패한다. 순환 참조를 만드는 대신 이 한 컬럼만 느슨하게 둔다.

`area_*` 4개 컬럼은 별도 테이블로 정규화하지 않았다. 대회당 한 나라고, 조인해서
얻을 것이 없다.

### seasons — 시즌

**현재 시즌만 저장한다.** 외부 응답의 `seasons[]`에는 과거 시즌이 딸려 오지만
쓰지 않는다. 스코프 밖이라는 이유가 첫째고, 기술적인 이유가 하나 더 있다 —
`winner_team_id`가 `teams`를 참조하는데 **과거 우승팀이 팀 마스터에 없다.**
팀 마스터는 현재 시즌 순위표·경기에서만 채워지므로, 강등된 팀이나 오래전
우승팀은 존재하지 않는다. 과거 시즌을 넣으면 FK가 깨진다.

`winner_team_id`는 nullable이다. 시즌이 끝나기 전에는 null로 온다.

### standings — 순위표

**PK가 6개 컬럼이다.**

```sql
PRIMARY KEY (competition_id, season_id, stage, type, group_name, team_id)
```

`(대회, 시즌, 팀)`이면 충분해 보이지만 그렇지 않다. 외부의 `standings[]`는
**배열**이고, `stage`(REGULAR_SEASON 등) / `type`(TOTAL·HOME·AWAY) /
`group`의 조합마다 블록이 하나씩 온다. 같은 팀이 같은 시즌에 TOTAL 행과
HOME 행으로 두 번 등장할 수 있다. 셋을 PK에서 빼면 한 팀의 순위 행들이
서로를 덮어쓴다.

5대 리그는 실제로 REGULAR_SEASON + TOTAL 단일 블록만 오지만, 구조로는 열어 둔다.

**`group_name`은 `NOT NULL DEFAULT ''`다.** 외부의 `group`은 null이 아니라
`"Matchday"` 같은 문자열이고 리그마다 다르다. PK 구성 요소는 null일 수 없으므로
(SQLite에서 PK 컬럼의 null은 조용히 중복을 허용한다), 값이 없으면 빈 문자열로 둔다.

**`form` 컬럼은 없다.** 외부 순위표의 `form`은 항상 null로 온다. 폼 가이드는
`matches`에서 직접 계산한다.

**순위 스냅샷은 없다.** 이 테이블은 (대회, 시즌, 팀)당 **한 행뿐**이고 수집할
때마다 덮어쓴다. 그래서 "3라운드 시점의 순위가 어땠나"를 복원할 방법이 없다.

경기 상세(`/matches/{id}`)에서 이 한계가 드러난다. 폼과 상대전적은 `matches`에서
계산하므로 "그 경기 이전"으로 좁힐 수 있지만, 순위만은 현재 값을 낼 수밖에 없다.
끝난 경기를 볼 때 셋의 기준 시점이 어긋난다는 뜻이다.

스냅샷을 남기려면 `(시즌, 라운드, 팀)`을 PK로 하는 이력 테이블이 필요하다.
20팀 x 38라운드 x 5리그면 시즌당 3,800행이라 크기는 문제가 아니지만, 지금
스코프에서 그 값을 쓸 화면이 없다. "나중에 필요할 수도"로 테이블을 미리 만들지
않는다는 규칙에 따라 두지 않았고, 대신 응답 스키마와 API 계약에 명시했다.

집계 컬럼(`won` `draw` `lost` `points` …)은 전부 NOT NULL이다. 순위표 행은
경기 수가 0이어도 0으로 채워져서 온다.

### matches — 경기

**점수 관련 컬럼에 NOT NULL을 걸지 않았다.** `score.fullTime` / `halfTime` /
`winner`는 **경기 전이면 전부 null**이다. 일정과 결과가 한 테이블에 함께
들어 있으므로 미래 경기 행은 점수가 비어 있는 것이 정상이다. NOT NULL을 걸면
일정을 저장할 수 없고, 0으로 채우면 "0-0 무승부"와 "아직 안 함"이 구별되지 않는다.

`matchday`도 nullable이다. 리그 경기에는 항상 오지만 플레이오프 등에서 빠질 수 있다.

**`utc_date`는 UTC 문자열 그대로 저장한다.** 로컬 타임존 변환은 표현 계층에서만
한다. DB에 현지 시각을 넣으면 서버 타임존이 바뀔 때 과거 데이터의 의미가 달라지고,
문자열 정렬이 곧 시간 정렬이라는 성질도 잃는다.

`id`는 여기서도 외부 id를 그대로 PK로 쓴다. 전역 고유하고, 재수집 시 같은 경기가
같은 행으로 떨어져야 upsert가 성립한다.

### ingest_runs — 수집 이력

유일하게 FK가 없는 테이블이다. `competition_code`를 외래키가 아니라 **문자열로**
들고 있는데, 의도된 것이다. 이 테이블은 **수집이 실패했을 때도 행을 남겨야 하고**,
실패한 상황에서는 참조 대상이 아직 DB에 없을 수 있다. FK를 걸면 "처음 수집이
실패했다"는 사실 자체를 기록할 수 없다.

`AUTOINCREMENT`를 쓴 유일한 테이블이기도 하다. 다른 테이블은 외부 id가 PK다.

## 🔍 인덱스

인덱스는 네 개뿐이다. 실제로 도는 쿼리에서 출발해 만들었다.

```sql
idx_matches_competition_season_date  (competition_id, season_id, utc_date)
idx_matches_home_status              (home_team_id, status, utc_date)
idx_matches_away_status              (away_team_id, status, utc_date)
idx_ingest_runs_lookup               (competition_code, resource, status, finished_at DESC)
```

**홈·원정에 인덱스를 따로 거는 이유** — 폼 가이드와 상대전적은 한 팀이 홈일 때와
원정일 때를 **모두** 세야 한다. 그래서 조회 조건이
`home_team_id = ? OR away_team_id = ?` 형태고, SQLite는 이 OR을 두 인덱스의
합집합으로 처리한다. 한쪽만 걸면 절반은 풀스캔이 된다.

세 인덱스 모두 `status`나 `utc_date`를 뒤에 붙였다. 폼 가이드는
"FINISHED 중 최신 N건"이라 필터와 정렬이 인덱스 안에서 끝난다.

`utc_date`를 뒤에 둔 것이 나중에 한 번 더 값을 했다. 경기 상세가 폼과
상대전적을 "그 경기 이전"으로 좁히면서 `utc_date < ?` 조건이 붙었는데,
같은 인덱스가 그대로 받는다. 같은 이유로 `idx_matches_competition_season_date`가
"같은 라운드의 다른 경기" 조회를 받는다 — 라운드로 좁히고 킥오프순으로 정렬하는
기존 목록 쿼리와 같은 모양이라 인덱스를 새로 만들지 않았다.

`ingest_runs` 인덱스는 헬스 엔드포인트의 "리그·리소스별 최신 1건" 쿼리
(윈도우 함수 `ROW_NUMBER`)를 위한 것이다.

`standings`에는 별도 인덱스가 없다. PK가 곧 조회 조건의 앞부분이라 그대로 쓰인다.

## ⚙️ 런타임 설정

| PRAGMA | 값 | 이유 |
| --- | --- | --- |
| `journal_mode` | `WAL` | 배치 쓰기와 API 읽기가 동시에 일어난다. 기본 저널이면 읽기가 쓰기를 막는다 |
| `foreign_keys` | `ON` | SQLite는 기본이 OFF다. 켜지 않으면 FK가 장식이 된다 |
| `busy_timeout` | 5000ms | 잠금 경합 시 즉시 실패 대신 잠시 기다린다 |
| `synchronous` | `NORMAL` | 쓰기 커넥션만. WAL에서는 이 수준으로 충분하다 |
| `query_only` | `ON` | **읽기 커넥션만.** 요청 경로의 쓰기를 런타임에서 막는다 |

**읽기와 쓰기 커넥션을 나눈 것이 핵심이다.** "요청 경로에서는 읽기만 한다"는
규칙을 주석이 아니라 런타임 에러로 강제한다. 읽기 커넥션에서 `query_only`가
켜져 있으면 실수로 들어간 upsert가 배포 후가 아니라 테스트에서 터진다.

`journal_mode`는 DB 파일에 새겨지는 영속 속성이라 한 번만 켜면 되지만, 쓰기
커넥션이 열릴 때마다 멱등하게 설정한다. "누가 먼저 열었는가"에 의존하지
않기 위해서다. 반대로 읽기 커넥션은 `journal_mode`를 건드리지 않는다 —
`query_only` 상태에서는 바꿀 수도 없고, WAL 설정은 초기화와 쓰기 쪽 책임이다.

**커넥션은 연 스레드 안에서만 쓴다.** `check_same_thread`는 기본값(True)을
유지한다. 이 결정의 배경은 [`architecture.md`](architecture.md)의
스레드 항목에 있다.

## 🔧 스키마 관리

마이그레이션 도구를 쓰지 않는다. `schema.sql` 전체를
`CREATE ... IF NOT EXISTS`로 멱등하게 적용하고, `python -m app.db.init_db`가
그 일을 한다. 앱 기동 시 자동으로 돌리지 않는다 — 기동이 스키마를 손대면
잘못된 배포가 조용히 DB를 바꿔 놓는다.

**한계를 알고 쓰는 것이 전제다.** `IF NOT EXISTS`는 이미 있는 테이블에
컬럼을 더하거나 타입을 바꾸지 못한다. 스키마를 바꿔야 하면 지금은
DB를 지우고 다시 만든 뒤 배치를 한 번 돌리는 것이 정해진 절차다.
수집은 매번 현재 시즌 전체를 다시 가져오므로 재구축 비용이 배치 한 사이클이고,
그래서 마이그레이션 도구 없이 버틸 수 있다.
