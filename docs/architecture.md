# 🏛️ 아키텍처

이 문서는 코드를 처음 보는 사람을 위한 것이다. "무엇이 있는가"보다
"왜 이렇게 나뉘어 있는가"를 적는다. 엔드포인트별 스키마는
[`../../docs/api-contract.md`](../../docs/api-contract.md)에, 실행 방법은
[`../README.md`](../README.md)에 있다.

---

## 🧭 출발점 — 왜 배치와 API를 갈랐나

football-data.org 무료 티어는 **분당 10회**다. 대시보드 화면 하나가
순위표 + 일정 + 팀 20개의 폼 가이드를 요청하면 그것만으로 한도를 넘긴다.
요청이 올 때마다 외부를 부르는 구조는 처음부터 성립하지 않는다.

그래서 시스템을 두 개의 프로세스로 나눴다.

- **수집 배치** (`ingest/`) — 외부 cron이 주기적으로 부른다. 외부 API를 읽어 SQLite에 쓴다.
- **API 서버** (`app/`) — SQLite만 읽는다. 외부로 나가는 코드가 아예 없다.

둘의 접점은 **SQLite 파일 하나**뿐이다. 큐도, 앱 내 스케줄러도, 백그라운드
태스크도 두지 않았다. 배치가 몇 분 늦어도 API는 마지막으로 수집된 데이터를
그대로 서빙하면 되고, API가 죽어도 수집은 계속된다.

이 분리에서 따라 나오는 규칙이 하나 있다. **응답이 비어 있다면 그건 "아직
수집되지 않은 것"이지 지금 채워야 할 것이 아니다.** 요청 경로에서 외부를
호출해 빈 곳을 메우는 순간 위의 계산이 무너진다.

## 🧱 계층

의존 방향은 한 방향이다. 역방향 import는 없다.

```
routers/  ──▶  services/  ──▶  repositories/  ──▶  db/
 (HTTP)        (도메인·계산)      (조회 SQL)       (커넥션·PRAGMA)
```

**`routers/`** — HTTP 계층. 경로·쿼리 파라미터 검증, 응답 모델 선언,
커넥션 열고 닫기까지. SQL을 직접 쓰지 않는다.

**`services/`** — 도메인 계층. 리포지토리가 돌려준 행을 응답 스키마로 조립하고,
DB에 없는 파생 값(폼 가이드, 상대전적)을 계산한다. **HTTP를 모른다** — 상태 코드도,
`HTTPException`도 여기 없다.

**`repositories/`** — SQL이 존재하는 유일한 곳. 단, **조회 전용**이다.
쓰기 SQL은 배치 쪽 `ingest/writers.py`에 따로 있다.

**`schemas/`** — Pydantic 응답 모델. 외부 camelCase를 snake_case로 재정의한다.

**`db/`** — 커넥션 수명주기와 PRAGMA, `schema.sql`.

**`leagues.py`** — 리그 레지스트리. 계층 바깥에 있고, 배치와 API가 함께 쓴다.

### 왜 조회와 쓰기 SQL을 갈랐나

같은 테이블을 다루니 한곳에 모으는 편이 자연스러워 보인다. 그러지 않은 이유는
두 SQL의 **성격이 다르기** 때문이다. 조회는 요청 경로에서 초당 여러 번 돌고,
쓰기는 배치 프로세스에서 몇 분에 한 번 돈다. 한 모듈에 섞어 두면
"이 함수는 어느 쪽에서 부르는 건가"를 매번 확인해야 하고, 요청 경로에서
실수로 upsert를 부르는 길이 열린다.

지금은 그 길이 코드 배치와 런타임 양쪽에서 막혀 있다. 읽기 커넥션은
`PRAGMA query_only=ON`이라 쓰기가 나가면 즉시 에러가 난다.

### 왜 서비스가 HTTP를 모르나

`services/`가 `HTTPException`을 던지면 배치나 CLI에서 같은 계산을 재사용할 수
없고, 테스트할 때도 FastAPI를 끌고 들어와야 한다. 대신 도메인 예외를 올린다.

| 도메인 예외 | 뜻 | 변환 |
| --- | --- | --- |
| `NotIngestedError` | 레지스트리엔 있으나 아직 수집 안 됨 | 404 |
| `InvalidFilterError` | 받아들일 수 없는 쿼리 파라미터 | 400 |

변환은 `app/main.py`의 예외 핸들러가 한 곳에서 맡는다.

**404가 두 종류인 것이 중요하다.** "없는 리그 코드"(`/competitions/XX/...`)와
"아는 리그인데 아직 수집 전"은 원인도 대응도 다르다. 전자는 클라이언트의 오타고,
후자는 배치를 확인해야 할 신호다. 메시지를 구분하지 않으면 프런트에서
둘을 똑같이 "없음"으로 그려 버리고, 수집이 멈춰 있다는 사실이 묻힌다.

**단, 레지스트리가 없는 리소스는 404가 한 종류다.** 팀과 경기가 그렇다.
`/teams/57`이나 `/matches/560542`의 id가 DB에 없을 때, 그게 틀린 id인지 아직
수집되지 않은 것인지 판단할 근거가 없다. 리그처럼 "우리가 다루기로 한 목록"이
없기 때문이다. 이 경우 구분하는 척하지 않고 "저장된 대상이 아니다" 하나로 낸다.

같은 이유로 **알 수 없는 `status` 필터는 400**이다. 빈 목록으로 돌려주면
오타와 "그 상태의 경기가 정말 없음"을 구분할 수 없다.

### 계층 경계는 테스트가 지킨다

문서에만 적어둔 의존 방향은 조용히 썩는다. 그래서 규칙을 실행 가능한 형태로
못 박아 두었다.

- `tests/test_layering.py` — `repositories/`·`services/`가 `fastapi`·`httpx` 등을
  import하지 않는지 AST로 확인하고, `python -c "import ingest.__main__"`을
  별도 프로세스로 돌려 FastAPI가 딸려 들어오지 않는지 본다.
- `tests/test_thread_safety.py` — 아래 스레드 규칙을 정적 검사와 동시 요청 양쪽으로 막는다.

## 🔁 요청 하나의 흐름

`GET /competitions/PL/teams/57/form` 을 예로 든다.

```
routers/teams.py
  ├ require_league("PL")        레지스트리에 없으면 여기서 404
  ├ limit 범위 검증 (1~20)       FastAPI Query 제약
  └ with read_connection():     ← 커넥션은 핸들러 본문에서 연다

services/form.py
  ├ resolve_current_season()    competitions + seasons 조회, 없으면 NotIngestedError
  ├ teams_repo.get_team()       저장된 팀이 아니면 NotIngestedError
  └ 결과 조립

repositories/matches.py
  └ FINISHED 경기를 홈/원정 양방향으로 최신순 N건, 행마다 W/D/L 을 SQL CASE 로

schemas/teams.py
  └ FormGuide 로 직렬화 → 200
```

커넥션의 **소유자는 라우터**다. 서비스와 리포지토리는 `conn`을 인자로 받기만
하고 열거나 닫지 않는다. 덕분에 한 요청 안에서 여러 리포지토리를 불러도
커넥션은 하나이고, 수명 경계가 `with` 블록 하나로 눈에 보인다.

## 🧩 조합 엔드포인트

`GET /matches/{match_id}`(경기 상세)는 다른 엔드포인트와 성격이 다르다.
한 화면에 필요한 것을 한 번에 준다 — 경기 자체, 양 팀의 순위와 폼, 상대전적,
같은 라운드의 다른 경기들. 프런트가 네댓 번 왕복하는 대신 백엔드가 조립한다.

**새로 계산하는 값은 없다.** 이미 다른 엔드포인트가 쓰는 조회를 모아 부를 뿐이다.
`services/match_detail.py`가 리포지토리를 여섯 번 호출하고 그 결과를 하나의
응답 모델로 엮는다.

**왜 거대한 SQL 하나로 합치지 않았나** — 조각 하나하나가 이미 다른 곳에서 쓰이기
때문이다. 폼 계산은 `/teams/{id}/form`과, 상대전적은 `/teams/{id}/vs/{id}`와,
같은 라운드 조회는 `/competitions/{code}/matches?matchday=N`과 같은 SQL이다.
조인 하나로 합치면 그 재사용이 끊기고, 승패 판정 같은 규칙이 두 벌이 된다.
쿼리 여섯 번은 SQLite 로컬 파일에서 무시할 수 있는 비용이고, 규칙이 한 곳에
남는 값어치가 그보다 크다.

**여기서 커넥션 규칙이 가장 크게 작동한다.** 쿼리가 여섯 번이어도 커넥션은
하나이고, 열기부터 닫기까지가 한 워커 스레드 안에 있다. 커넥션을 의존성으로
주입했다면 이 엔드포인트가 동시 요청에서 가장 먼저 깨졌을 것이다.
그래서 `tests/test_thread_safety.py`의 엔드포인트 목록에 이것도 들어 있다.

**기준 시점이 섞여 있다는 점은 알고 써야 한다.** 폼과 상대전적은 그 경기의
`utc_date` **이전**만 본다 — 끝난 경기라면 "그 경기에 들어갈 때"의 값이다.
반면 순위는 **현재 값**이다. 순위표를 덮어쓰기 때문에 과거 시점을 복원할 수
없어서다. 자세한 배경은 [`database.md`](database.md)의 순위 스냅샷 항목에 있다.

## 🧵 커넥션을 의존성으로 주입하지 않는 이유

여기가 이 프로젝트에서 가장 비직관적인 결정이라 따로 적는다.

FastAPI는 동기 핸들러를 워커 스레드 풀에서 돌린다. SQLite 커넥션은 만든
스레드에서만 쓸 수 있어서, 요청 하나가 스레드를 넘어가면
`sqlite3.ProgrammingError`로 500이 난다.

교과서적인 `Depends(get_db)`가 정확히 그 상황을 만든다. 동기 제너레이터
의존성은 **진입 / 핸들러 본문 / 정리를 FastAPI가 각각 별도의
`anyio.to_thread.run_sync`로 돌린다.** 요청이 몰려 워커가 재배치되면 커넥션을
연 스레드와 쓰는 스레드가 갈린다. 정리(`close`)도 또 다른 스레드에서 돌아
같은 이유로 터진다.

- **해법** — `with read_connection():`을 핸들러 함수 **본문 안**에 둔다.
  동기 핸들러 본문은 통째로 한 워커 스레드에서 실행되므로 열기·조회·닫기가
  한 스레드에 묶인다.
- **`check_same_thread=False`는 해법이 아니다** — 가드만 끌 뿐 공유는 그대로
  남는다. 터지는 대신 조용히 깨진다. 기본값(True)을 유지한다.
- **단발 요청으로는 절대 안 드러난다** — 워커가 재배치되지 않아 항상 통과한다.
  회귀는 동시 요청 테스트로만 잡힌다.

## 🏆 리그 레지스트리

리그 추가는 코드 수정이 아니라 `app/leagues.py`의 `LEAGUES`에 항목 하나를
더하는 것으로 끝나야 한다. 그래서 어디에도 `if code == "PL"` 같은 분기가 없다.
수집기 세 개도 전부 같은 시그니처(`collect(client, conn, league) -> int`)를
갖고, 리그를 인자로만 받는다.

`leagues.py`는 **프레임워크를 import하지 않는다.** 이게 사소해 보이지만
의도적이다. 배치가 이 모듈을 그대로 쓰기 때문이다. 여기서 `HTTPException`을
던지면 FastAPI 없이 도는 `python -m ingest`가 웹 프레임워크를 끌고 들어온다.
그래서 조회 실패는 `LookupError`로 올리고, 404로 바꾸는 어댑터는
`routers/deps.py`에 따로 둔다.

**`code`가 라우팅 키다.** URL에는 `PL`을 쓰고, football-data.org의 숫자
`external_id`(2021 등)는 외부 호출에만 쓴다. 외부 벤더의 식별자를 우리 API
표면에 노출하지 않기 위해서다. 반대로 **팀은 전역 고유 id를 경로에 그대로
쓴다**(`/teams/57`) — 팀 id는 리그·시즌과 무관하게 고유하고, 별도의 코드 체계가 없다.

## 📐 스코프

지금 하지 않기로 한 것들이다. "나중에 필요할 수도"로 테이블이나 필드를 미리
만들지 않는다는 규칙과 짝이다.

- **현재 시즌만** — 과거 시즌 백필은 하지 않는다.
- **실시간 스코어 없음** — 배치 주기만큼의 지연을 받아들인다.
- **로그인·유저 없음** — 인증 계층 자체가 없다.
- **상세 스탯 없음** — 라인업·카드·점유율·배당은 저장하지 않는다.
